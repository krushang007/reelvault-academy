    Microsoft System Design Interview: Solving the Token Refresh Stampede Race Condition

    Executive Summary

    In modern mobile and single-page web applications, authentication relies on short-lived JWT access tokens (e.g., 15–60 minutes) paired with long-lived refresh tokens. While secure, this architecture triggers a notorious client-side production failure known as the Token Refresh Stampede.

    In this technical breakdown of his Round 4 System Design and Implementation interview with Microsoft, engineer Ankit explains the exact problem statement presented by the engineering lead: when an access token expires, multiple parallel network requests fail simultaneously with HTTP 401 Unauthorized, spawning concurrent refresh requests that race against the identity provider, invalidate one another via Refresh Token Rotation, and forcefully log the user out.

    Core Visual Demonstrations

    The Failure Mechanism: Why Naive 401 Handlers Break

    1. Parallel Screen Loading: When a user opens their dashboard or home feed, the application immediately fires 4 to 6 concurrent API calls (e.g., /api/user/profile, /api/feed, /api/notifications, /api/messages).
    2. Simultaneous Expiration: Because the access token expired 2 seconds ago, all 5 requests receive 401 Unauthorized at the exact same millisecond.
    3. The Stampede: If each request naively tries to catch the 401 and invoke POST /auth/refresh, 5 simultaneous refresh requests hit the authentication server.
    4. Refresh Token Rotation Crash: Production auth servers (Auth0, Supabase, Cognito, Firebase) implement Refresh Token Rotation: as soon as a refresh token is exchanged, it is immediately revoked and replaced with a new one. The first request succeeds; the remaining 4 requests arrive with an already-revoked refresh token. The auth server treats this as a replay attack and terminates the entire user session.

    The Production Solution: Interceptor Mutex & Request Queue

    The correct pattern introduces a synchronization barrier inside the HTTP client (Axios, Fetch interceptor, or Retrofit Authenticator):

    • Boolean Mutex Flag (isRefreshing): Tracks whether a refresh network roundtrip is currently in flight.
    • Callback Retry Queue (failedQueue): Holds the pending promises of all subsequent 401 requests until the single token refresh operation settles.

    TypeScript / Axios Implementation Pattern

    import axios, { AxiosError, InternalAxiosRequestConfig } from 'axios';

let isRefreshing = false;
let failedQueue: Array<{
  resolve: (token: string) => void;
  reject: (error: any) => void;
}> = [];

const processQueue = (error: any, token: string | null = null) => {
  failedQueue.forEach((promise) => {
    if (error) {
      promise.reject(error);
    } else if (token) {
      promise.resolve(token);
    }
  });
  failedQueue = [];
};

apiClient.interceptors.response.use(
  (response) => response,
  async (error: AxiosError) => {
    const originalRequest = error.config as InternalAxiosRequestConfig & { _retry?: boolean };

    // Detect 401 and avoid infinite loops
    if (error.response?.status === 401 && !originalRequest._retry) {
      if (isRefreshing) {
        // Queue the request until the active refresh completes
        return new Promise((resolve, reject) => {
          failedQueue.push({ resolve, reject });
        })
          .then((newToken) => {
            originalRequest.headers.Authorization = `Bearer ${newToken}`;
            return apiClient(originalRequest);
          })
          .catch((err) => Promise.reject(err));
      }

      originalRequest._retry = true;
      isRefreshing = true;

      try {
        const { data } = await axios.post('/auth/refresh', {
          refreshToken: getStoredRefreshToken(),
        });

        const newAccessToken = data.accessToken;
        saveTokens(newAccessToken, data.refreshToken);

        // Update authorization header for original request
        originalRequest.headers.Authorization = `Bearer ${newAccessToken}`;

        // Flush all queued pending requests with the new token
        processQueue(null, newAccessToken);

        return apiClient(originalRequest);
      } catch (refreshError) {
        processQueue(refreshError, null);
        logoutUserAndRedirect();
        return Promise.reject(refreshError);
      } finally {
        isRefreshing = false;
      }
    }

    return Promise.reject(error);
  }
);

    Key Architectural Takeaways

    • Single In-Flight Guarantee: Exactly one /auth/refresh network request is executed, completely eliminating race conditions.
    • Transparent Replay: Callers awaiting getFeed() or getProfile() never see the 401 error; their promises pause until the fresh token is injected and their calls resolve successfully.
    • Unified Failure Mode: If the refresh token itself is truly expired or revoked, processQueue(refreshError) cleanly rejects all waiting callers and routes the user to the login screen once.
